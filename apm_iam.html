ServiceNow APM · CMDB Extension

Application Security Data Model

One auth profile per application, with unbounded child records for SAML federations and OAuth/OIDC trust relationships — supporting multiple SP/IdP and Relying Party/Authorization Server connections per app.
Parent CI (1 per app)
Child table (many per app, linked to parent)
cmdb_ci_appl (extended)
cmdb_ci_app_auth_profile
Application Authentication & Authorization Profile. One record per app.
iam_domain: Workforce IAM / Customer IAM
Which identity population this app serves — employees/contractors (Workforce IAM) or customers/consumers (Customer IAM).
identity_provider: PingOne AIC, Azure AD, PingFed…
The platform that actually authenticates the user and issues tokens/assertions for this app.
authentication_protocol: OAuth2.0, SAML 2.0, LDAP…
The standard used to exchange identity between the app and the IdP.
authentication_flow: Auth Code+PKCE, Client Creds…
The specific sequence of steps used to obtain a token — determines how secure and how automatable the login is.
token_format: JWT, SAML Assertion, Opaque
The shape of the credential issued after authentication — whether it's self-contained (JWT) or a reference the app must validate against the IdP (Opaque).
mfa_required: true / false
Whether a second authentication factor is enforced before access is granted.
principal_type: Internal Users, External Users, Service Accounts
Who or what authenticates to this app — employees, external/customer users, or non-human service accounts.
client_type: SPA, Server-side Web App, Native/Mobile, Machine-to-Machine
The OAuth client classification for this app. Determines whether login_experience below even applies — it's only relevant for SPA clients.
login_experience: Hosted Login (IdP Redirect) / Embedded Login (Custom UI + IAM API)
Applies when client_type = SPA. Hosted Login means the app redirects to the IdP's own login page — the app never touches credentials. Embedded Login means the app renders its own login UI and calls IAM APIs directly for a richer, in-app experience — this shifts credential handling and more security responsibility onto the app team.
child table
cmdb_ci_saml_federation
One row per SAML federation partner. Minimal field set: role, partner, entity ID, SSO URL.
saml_role: Service Provider (SP) / Identity Provider (IdP)
Whether this app relies on the partner to authenticate the user (SP) or authenticates the user and issues the assertion to the partner (IdP).
federation_partner: string
The name of the other party in this SAML relationship (e.g., "Salesforce," "Workday," or another internal app).
entity_id: string (SP or IdP issuer)
The unique SAML identifier for each side of the exchange — your app's ID if you're the SP, or your issuer ID if you're the IdP.
sso_url: URL
Where the authentication handoff happens — the IdP's SSO endpoint you send users to, or the endpoint your app exposes if you are the IdP.
child table
cmdb_ci_oauth_trust_relationship
One row per OAuth/OIDC trust relationship. Minimal field set: client ID and grant type only.
client_id: string
The identifier the authorization server issues to this app so it can be recognized when requesting tokens.
grant_type: Auth Code+PKCE, Client Creds, Custom
The OAuth flow this app uses to obtain a token — depends on whether a human user, a service, or a custom process is involved.
Notes —
· An app that is both SP and IdP simply has multiple cmdb_ci_saml_federation rows with different saml_role values.
· Each child table row links back to its parent cmdb_ci_app_auth_profile record (reference field not shown here for readability), driving a related list on the Application CI form.
· Naming follows SAML 2.0, OAuth 2.0 (RFC 6749), and OIDC spec vocabulary rather than generic CRUD labels — keeps the model self-documenting for architects and auditors.
· Child tables are intentionally kept lean (only the fields requested) — extend later if reporting or audit needs grow.
